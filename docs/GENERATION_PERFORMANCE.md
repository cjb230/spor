# Example generation performance

The generator runs the native Rust engine and MCB teacher. On the M4 Pro used
here there are 10 performance and 4 efficiency cores. Storage is a small share
of total cost: an initial 2,048-example profile measured 18.08 seconds of native
generation and 0.010 seconds for compression, hashing and file writes.

Builder has subsequently been optimized; see the
[Builder optimization report](../benchmarks/builder-optimization-2026-11-22/RESULTS.md)
for the current implementation, equivalence checks and measurements. The queue
comparison below records the earlier implementation.

The current Builder-optimized worker measured **1,314–1,360 examples/second**
over repeated 32,768-example runs at 14 threads. A subsequent complete run
generated **40M training + 100K validation examples in 34,500 seconds**
(user-reported elapsed time), about **9 hours 35 minutes** or **1,162 total
examples/second**. Its shards occupy **916 MB**. Use this sustained result for
planning: approximately **30 hours for 125M**, excluding training, if the rate
holds. See the [completed-run summary](../benchmarks/builder-optimization-2026-11-22/completed-40m.json).

## Queue and reuse

Replace eight-game barriers with a bounded queue of independently seeded games.
Jobs may finish out of order, while results and resume cursors are emitted in
game-counter order. Retain completed future games across requests with the same
seed, split, strategies, trace mode and continuation cursor. A configuration
change or rewind invalidates the queue; queued stale work is cancelled.

Discard surplus rows only within the final consumed game, as the original
protocol did. Retain whole future games instead of recomputing them. Shard and
request boundaries, labels and deterministic ordering remain compatible with the
original implementation. Rebuilding changes the worker hash, so an interrupted
dataset generated by the old binary must continue using that old binary or start
a fresh dataset; completed datasets remain usable for training.

## Measured comparison

Four successive 1,024-row requests used MCB:16, seed 2001, and the same
Builder/Tactician/Planner/MCB:16 opponents. The old executable was saved before
the change. All runs below used identical requests and were measured sequentially
after confirming that a background Rust test run had stopped.

| Worker | Threads | Seconds | Examples/s | Average CPU cores |
|---|---:|---:|---:|---:|
| Before | 8 | 39.86 | 102.7 | 4.76 |
| Queue and reuse | 8 | 26.45 | 154.9 | 7.87 |
| Queue and reuse | 10 | 23.46 | 174.6 | 9.59 |
| Queue and reuse | 14 | 22.95 | 178.5 | 10.84 |

The same-thread improvement is 51%; using 14 threads improves throughput by 74%
over the old default. Ten and fourteen threads are close in this short test;
one run per setting does not establish a reliable difference between them.
These are short native-generation measurements, not sustained corpus throughput
guarantees. At the measured 14-thread rate, 40 million and 125 million examples
would take about 2.6 and 8.1 days respectively, excluding training; live ETA
should replace that extrapolation during long runs.

All four runs produced the same row SHA-256
`e225ab91e89998f2136f4d0fd922dbfcea97994e4de706ce6f5ab98544dd18c1`,
the same per-request next-game cursors `[40, 80, 120, 161]`, and the same
94,997-byte compressed shard. Shutdown took approximately 1 ms at 10 and 14
threads, so prefetched games did not delay process exit. Average CPU cores
means summed child-process CPU seconds divided by wall seconds, not a measure
of equivalent P/E-core computing power.

The [raw results](../benchmarks/generation-queue-2026-11-22/results.json) include
worker/source hashes and identify excluded initial measurements. To repeat a
short native benchmark from the repository root:

```sh
python -m benchmarks.generation_queue \
  --worker rust/target/release/examples/neural_generate \
  --threads 14 --output models/queue-benchmark-14.json
```

Run thread-count comparisons sequentially to avoid CPU contention.

## Future optimizations

These were recorded after the queue change:

1. **Specialize Builder's rollout move selection — implemented.** Avoid constructing and
   sorting full candidate lists, copying unused board state and allocating new
   scratch caches for every simulated turn. Preserve scoring, claims and ties.
2. **Provide a move-selection-only Monte Carlo path.** Callers needing only a
   move and claims can avoid constructing sorted estimates for every move.
3. **Eliminate hopeless candidates with exact bounds.** Stop simulating a
   candidate only when it cannot become the winner under any remaining sample
   outcomes, including the existing heuristic and action-order tie breakers.

Profile the remaining hot paths and test byte-identical decisions before and
after each optimization. Lower sampling, different rollout policies or cheaper
opponents change the teacher or dataset distribution and should be measured as
separate experiments.

## Storage

Packed rows are 200 bytes before compression. The baseline's 4,096 examples
occupy 94,997 bytes as one compressed NPZ shard: 23.19 bytes per example. At
that rate 125 million examples occupy 2.90 GB (2.70 GiB), and 40 million occupy
0.93 GB. Real compression varies with corpus diversity and shard size. Reserve
5–10 GB for the larger corpus plus its validation, logs and working files.
